    37→    37→## 1. EXECUTIVE SUMMARY
    38→    38→
    39→    39→### 1.1 The Project
    40→    40→
    41→    41→Doctorooms is a multi-role healthcare appointment management platform being rebuilt from a PHP/CodeIgniter monolith to Next.js 16. It serves 7 user roles: Patient, Doctor, Receptionist, Hospital, Assistant, Pharmacist, and Admin.
    42→    42→
    43→    43→### 1.2 Current State — By The Numbers
    44→    44→
    45→    45→```
    46→    46→Pages:           61 dashboard + 11 public = 72 total
    47→    47→API Routes:      101 files, ~150 endpoints
    48→    48→DB Models:       30 (Prisma)
    49→    49→Dependencies:    47 production, 8 dev
    50→    50→Components:      40+ shadcn/ui + 9 custom
    51→    51→Total LOC:       ~30,000+ (estimated)
    52→    52→```
    53→    53→

    70→    70→The platform suffers from three systemic issues:
    71→    71→

   228→   228→
   229→   229→### 3.2 Architecture Principles
   230→   230→
   231→   231→| # | Principle | Description |
   232→   232→|---|-----------|-------------|
   233→   233→| 1 | **Patient First** | Every decision prioritizes the patient journey. Revenue comes from bookings. |
   234→   234→| 2 | **Validate Everything** | All API inputs validated with Zod. All outputs typed. No exceptions. |
   235→   235→| 3 | **Extract, Don't Duplicate** | Shared logic in `lib/`, `hooks/`, `types/`, `components/`. DRY at all levels. |
   236→   236→| 4 | **Fail Gracefully** | Error boundaries, loading states, empty states, error toasts — always. |
   237→   237→| 5 | **Secure by Default** | httpOnly cookies, ownership checks, input sanitization, no raw IDs in responses. |
   238→   238→| 6 | **Server When Possible** | Use server components for data-heavy pages. Client only for interactivity. |
   239→   239→| 7 | **Batch Over N+1** | Never make N API calls when 1 batch call will do. |
   240→   240→| 8 | **Real-Time Over Polling** | Use WebSocket for chat, notifications, queue positions. |

   244→   244→## 4. ARCHITECTURE DECISION RECORDS (ADRs)
   245→   245→
   246→   246→### ADR-001: Authentication — Custom Cookie (Keep)
   247→   247→
   248→   248→- **Status**: ACCEPTED
   249→   249→- **Context**: System uses custom `doctorooms_session` cookie (raw user ID) instead of NextAuth JWT
   250→   250→- **Decision**: Keep custom cookie auth for API routes. Fix security (add random token, make httpOnly)
   251→   251→- **Rationale**: Works reliably, simple to debug, no NextAuth dependency. NextAuth config exists but is unused dead code.
   252→   252→- **Consequences**: Must add session token rotation and httpOnly flag. Must remove dead `auth.ts` NextAuth config.
   253→   253→
   254→   254→### ADR-002: Validation — Adopt Zod for All APIs
   255→   255→
   256→   256→- **Status**: PROPOSED
   257→   257→- **Context**: Currently all API validation is manual (`if (!body.name) return error`). Inconsistent, missing checks.
   258→   258→- **Decision**: Create Zod schemas for every API request body. Validate at route handler entry point.
   259→   259→- **Rationale**: Zod v4 is already a dependency. Provides type inference, auto-parsing, consistent error messages.
   260→   260→- **Consequences**: ~101 route files need Zod schemas. Schemas go in `src/lib/validations/`.
   261→   261→
   262→   262→### ADR-003: File Upload — Local Disk (Current Phase)
   263→   263→
   264→   264→- **Status**: ACCEPTED
   265→   265→- **Context**: Medical document upload is fake (metadata only). Avatar upload works but writes to `public/`.
   266→   266→- **Decision**: Phase 1-3: Local disk (`uploads/` with Bun file API). Phase 4+: Abstract to storage interface for S3/GCS.
   267→   267→- **Rationale**: SQLite + local disk is sufficient for dev/MVP. Production needs cloud storage.
   268→   268→- **Consequences**: Need `src/lib/storage.ts` abstraction layer. File serving via Next.js API route (not public/).
   269→   269→
   270→   270→### ADR-004: Real-Time — Socket.io (Existing Service)
   271→   271→
   272→   272→- **Status**: PROPOSED
   273→   273→- **Context**: Chat service exists at `mini-services/chat-service/` (port 3003) but is unused. All real-time is HTTP polling (10s).
   274→   274→- **Decision**: Activate Socket.io for: (1) Chat messages, (2) Notification push, (3) Queue position updates, (4) Booking status changes.
   275→   275→- **Rationale**: Service exists, just needs wiring. Eliminates 10s polling. Better UX for chat.
   276→   276→- **Consequences**: Frontend needs Socket.io client. Auth needs to pass through gateway.
   277→   277→
   278→   278→### ADR-005: Component Architecture — Extract From Monoliths
   279→   279→
   280→   280→- **Status**: PROPOSED
   281→   281→- **Context**: 3 page files are 700-800 lines. `StarRating` duplicated. `statusColors` in 4+ files.
   282→   282→- **Decision**: Decompose monolith pages into focused components. Extract shared pieces to `src/components/` and `src/hooks/`.
   283→   283→- **Rationale**: Maintainability, testability, reusability. Pages should be orchestrators, not implementations.
   284→   284→- **Consequences**: Each 800-line file becomes 1 page (200 lines) + 4-5 components (100-150 lines each).
   285→   285→
   286→   286→### ADR-006: Types — Centralize in `src/types/`
   287→   287→
   288→   288→- **Status**: PROPOSED
   289→   289→- **Context**: All types are inline in page files. `AuthUser` duplicated. `statusColors` in 4 files.
   290→   290→- **Decision**: Create `src/types/` with domain-specific type files. Import from there.
   291→   291→- **Rationale**: Single source of truth. Auto-completion. Prevents drift.
   292→   292→- **Consequences**: Need to create type files, then update all imports across 61+ pages.
   293→   293→
   294→   294→### ADR-007: Database — Stay SQLite for Dev, Prepare PostgreSQL Migration
   295→   295→
   296→   296→- **Status**: ACCEPTED
   297→   297→- **Context**: Current DB is SQLite. `.env.example` shows Supabase PostgreSQL config (commented out).
   298→   298→- **Decision**: Keep SQLite for all development. Schema must be PostgreSQL-compatible (no SQLite-specific features). Migration script exists at `scripts/switch-to-supabase.sh`.
   299→   299→- **Rationale**: SQLite is zero-config for dev. Prisma abstracts the DB layer. Switch is one config change.
   300→   300→- **Consequences**: No raw SQL queries. No SQLite-specific functions. Test migration before production.
   301→   301→
   302→   302→### ADR-008: Middleware — Add `middleware.ts` for Route Protection
   303→   303→
   304→   304→- **Status**: PROPOSED
   305→   305→- **Context**: Currently all dashboard route protection is client-side (useEffect in layout). Pages flash before redirect.
   306→   306→- **Decision**: Add Next.js `middleware.ts` that checks `doctorooms_session` cookie and redirects unauthenticated users to `/login`.
   307→   307→- **Rationale**: Server-side protection prevents flash. Faster redirect (no JS execution needed). More secure.
   308→   308→- **Consequences**: Middleware can't do DB lookups (edge runtime). Cookie-only check is sufficient for redirect — API routes still do full auth.

   394→   394→
   395→   395→```
   396→   396→Phase 0: Foundation          → Seed DB + Fix 5 critical bugs + Fix auth security

   398→   398→Phase 2: Workflow Engine      → Doctor 46% → 80%, Reception 55% → 80%
   399→   399→Phase 3: Supporting Roles     → Hospital 20% → 70%, Assistant 30% → 70%, Pharmacist 25% → 70%
   400→   400→Phase 4: Admin & Governance   → Admin 31% → 85%
   401→   401→Phase 5: Hardening            → All modules → 95%+
   402→   402→```

   404→   404→**Rationale for this order:**
   405→   405→- Patient FIRST: Revenue comes from patient bookings. No patients = no platform.
   406→   406→- Doctor + Reception SECOND: They process the bookings patients create. Without them, bookings sit in "Pending" forever.
   407→   407→- Supporting roles THIRD: Assistant and Pharmacist support doctors. Hospital is a separate entity.
   408→   408→- Admin LAST: Admin is governance/maintenance. Not revenue-generating. Can wait.

   875→   875→## 14. API ARCHITECTURE STANDARDS
   876→   876→
   877→   877→### 14.1 Route Handler Template
   878→   878→
   879→   879→Every API route MUST follow this pattern:
   880→   880→
   881→   881→```typescript
   882→   882→// src/app/api/example/route.ts
   883→   883→import { NextRequest, NextResponse } from 'next/server';
   884→   884→import { requireRole } from '@/lib/api-auth';
   885→   885→import { db } from '@/lib/db';
   886→   886→import { z } from 'zod';
   887→   887→
   888→   888→// 1. Validation schemas (at top of file)
   889→   889→const CreateBodySchema = z.object({
   890→   890→  name: z.string().min(1, 'Name is required').max(100),
   891→   891→  email: z.string().email('Invalid email'),
   892→   892→  status: z.enum(['Active', 'Inactive']).optional(),
   893→   893→});
   894→   894→
   895→   895→// 2. Type inference from schema
   896→   896→type CreateBody = z.infer<typeof CreateBodySchema>;
   897→   897→
   898→   898→// 3. Route handler
   899→   899→export async function POST(req: NextRequest) {
   900→   900→  // 3a. Auth check
   901→   901→  const user = await requireRole(req, 'patient');
   902→   902→  if (!user) {
   903→   903→    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   904→   904→  }
   905→   905→
   906→   906→  // 3b. Parse + validate body
   907→   907→  let body: CreateBody;
   908→   908→  try {
   909→   909→    const raw = await req.json();
   910→   910→    body = CreateBodySchema.parse(raw);
   911→   911→  } catch (err) {
   912→   912→    if (err instanceof z.ZodError) {
   913→   913→      return NextResponse.json(
   914→   914→        { error: 'Validation failed', details: err.errors },
   915→   915→        { status: 400 }
   916→   916→      );
   917→   917→    }
   918→   918→    return NextResponse.json({ error: 'Invalid request body' }, { status: 400 });
   919→   919→  }
   920→   920→
   921→   921→  // 3c. Business logic
   922→   922→  try {
   923→   923→    const record = await db.example.create({
   924→   924→      data: { ...body, userId: user.id },
   925→   925→    });
   926→   926→    return NextResponse.json({ record }, { status: 201 });
   927→   927→  } catch (error) {
   928→   928→    console.error('POST /api/example:', error);
   929→   929→    return NextResponse.json(
   930→   930→      { error: 'Internal server error' },
   931→   931→      { status: 500 }
   932→   932→    );
   933→   933→  }
   934→   934→}
   935→   935→```
   936→   936→
   937→   937→### 14.2 Response Standards
   938→   938→
   939→   939→```typescript
   940→   940→// Success
   941→   941→{ data: T }                    // Single item
   942→   942→{ items: T[], total: number }  // List with total
   943→   943→{ success: true, ... }         // Mutation acknowledgment
   944→   944→
   945→   945→// Error
   946→   946→{ error: string }              // Human-readable message
   947→   947→{ error: string, details: ZodError[] }  // Validation errors
   948→   948→```

   950→   950→### 14.3 Auth Patterns
   951→   951→
   952→   952→```typescript
   953→   953→// Role-required (most common)
   954→   954→const user = await requireRole(req, 'patient');
   955→   955→if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   956→   956→
   957→   957→// Any authenticated user
   958→   958→const user = await requireAuth(req);
   959→   959→if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   960→   960→
   961→   961→// Ownership check (after auth)
   962→   962→if (record.userId !== user.id) {
   963→   963→  return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
   964→   964→}
   965→   965→```

  1044→  1044→
  1045→  1045→1. **No SQLite-specific features** — use only Prisma-compatible types
  1046→  1046→2. **All strings have `@default('')`** — never null strings
  1047→  1047→3. **All numbers have `@default(0)`** — never null numbers

  1049→  1049→5. **JSON fields use `String` type** — Prisma SQLite doesn't support Json type natively
  1050→  1050→6. **Cascade deletes** — use `onDelete: Cascade` for owned relationships
