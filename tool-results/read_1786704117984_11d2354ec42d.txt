    12→### A1. Validation Library: Zod
    13→- `zod` v4.0.2 already installed in `package.json`
    14→- `react-hook-form` + `@hookform/resolvers/zod` also installed
    15→- **Decision**: Create centralized zod schemas in `src/lib/validations/`, use in both API routes (server-side) and forms (client-side)
    16→
    17→### A2. Emit Helper: Fire-and-Forget
    18→- Create `src/lib/emit-notification.ts` as a single-point helper
    19→- Use `fetch()` with no `await` — fire-and-forget pattern inside `.catch(() => {})`
    20→- Never let notification failures block business logic
    21→
    22→### A3. Pagination Pattern: Unified Cursor
    23→- Use existing `ipd-bills` pagination pattern as the standard: `{ page, limit, total, totalPages, data }`
    24→- Query params: `?page=1&limit=20&search=&status=`
    25→- Apply to all unbounded list endpoints
    26→
    27→### A4. Session Security: Phased Approach
    28→- Phase 1 (this plan): Add production guards + httpOnly role cookie + deduplicate DEV_USERS
    29→- Phase 2 (future): Replace session=userId with random session tokens in DB
    30→- Phase 3 (future): Add Next.js middleware for route-level auth
    31→
    32→### A5. Schema Safety: Restrict > Cascade
    33→- For critical parent records (Hospital, Ward, Bed, IpdAdmission) → use `onDelete: Restrict`
    34→- For child records (BillLineItem, Notification) → use `onDelete: Cascade`
    35→- Never silently delete parent records that have active children

   381→### Standard Pattern (from existing `ipd-bills/route.ts`)

   383→// Query params
   384→const page = parseInt(searchParams.get('page') || '1')
   385→const limit = parseInt(searchParams.get('limit') || '20')
   386→
   387→// Query
   388→const [data, total] = await Promise.all([
   389→  db.model.findMany({ where, skip: (page - 1) * limit, take: limit, ...includes }),

   391→])
   392→
   393→// Response
   394→return NextResponse.json({
   395→  data,
   396→  page, limit, total,
   397→  totalPages: Math.ceil(total / limit),
   398→})
   399→```

   431→## GAP 6: SCHEMA FK & DATA INTEGRITY
   432→### Problem
   433→24 FK relations missing `onDelete`, 4 `@unique` fields with `@default("")` causing SQLite constraint violations.
   434→
   435→### Step 6.1: Add onDelete to All FK Relations
   436→
   437→#### Strategy:
   438→- **`Restrict`** — When parent has active children that should NOT be auto-deleted
   439→- **`Cascade`** — When children are meaningless without parent (line items, notifications)
   440→- **`SetNull`** — When the reference is optional and should survive parent deletion
   441→
   442→#### Critical Relations (Must Fix):
   443→
   444→| Model | Field | References | onDelete | Reason |
   445→|-------|-------|------------|----------|--------|
   446→| IpdAdmission | hospitalId | Hospital | **Restrict** | Never delete hospital with active admissions |
   447→| IpdAdmission | wardId | Ward | **Restrict** | Never delete ward with active patients |
   448→| IpdAdmission | bedId | Bed | **Restrict** | Never delete bed with active admission |
   449→| IpdAdmission | departmentId | Department | **Restrict** | Preserve referential integrity |
   450→| IpdAdmission | attendingDoctorId | Doctor | **Restrict** | Doctor deletion shouldn't cascade to admissions |
   451→| NursePatientAssignment | bedId | Bed | **Restrict** | Active assignment locks the bed |
   452→| NursePatientAssignment | admissionId | IpdAdmission | **Cascade** | Assignment belongs to admission |
   453→| IpdBill | admissionId | IpdAdmission | **Restrict** | Bill survives admission for records |
   454→| IpdBill | hospitalId | Hospital | **Restrict** | Bill is financial record |
   455→| BillLineItem | billId | IpdBill | **Cascade** | Line items belong to bill |
