    42→## 9.2 Cron Jobs
    43→
    44→### 9.2.1 Crownjob Controller (`/application/controllers/Crownjob.php`)
    45→- **Extends**: `Guest_controller`
    46→- **Model loaded**: `Users_model` (aliased as `user`)
    47→
    48→#### `birthReminder()`
    49→- **Purpose**: Sends birthday SMS to patients whose birthday is today
    50→- **Data source**: `Users_model->get_today_birthday()` which joins `users`, `booking`, and `users AS docusers` to find patients who booked with doctors, filtered by `date_of_birth = today`
    51→- **Message format**: "Happy Birthday Dear {name} Stay Healthy... From Dr.{doctor_name} (DOCTOROOMS) (https://doctorooms.com)"
    52→- **SMS Provider**: `sms.soft-techsolutions.com` via HTTP GET with hardcoded API key
    53→- **Issues**:
    54→  - Hardcoded SMS API credentials in source code (security risk)
    55→  - Indian phone prefix `+91` hardcoded (not internationalized)
    56→  - Returns after first birthday (loop has early `return` instead of `continue`)
    57→  - No logging of sent/failed messages
    58→  - URL-encodes spaces but other special chars may break
    59→  - The `date_of_birth` column on `booking` table is used (not on `users`), meaning only patients who have booked appointments are eligible

    63→## 9.3 Notification System
    64→
    65→### 9.3.1 Notifications_model (`/application/models/Notifications_model.php`)
    66→- **Table**: `notifications`
    67→- **Columns**: id, user_id, title, body, status (READ/UNREAD), created_at, updated_at
    68→- **Methods**:
    69→  - `create($data)` - Creates notification with auto-timestamps
    70→  - `update($user_id, $data)` - Updates ALL notifications for a user (design flaw: should update by notification id)
    71→  - `get_all_by_user($user_id, $limit)` - All notifications ordered by created_at DESC
    72→  - `get_all_by_user_by_status($user_id, $limit)` - Unread notifications only
    73→  - `get_count_by_user($user_id)` - Count of unread notifications
    74→
    75→### 9.3.2 Notification Triggers (Cross-Module)
    76→
    77→Every appointment status change triggers notifications to both the patient AND the doctor's receptionist (if one exists):
    78→
    79→| Trigger Event | Controller | Notify: Patient | Notify: Receptionist |
    80→|---------------|------------|-----------------|---------------------|
    81→| New booking created | `Book.php` | Yes | Yes |
    82→| Booking canceled by patient | `Appointment.php` (patient) | - | Yes (to doctor) |
    83→| Doctor extends appointment | `doctor/Appointment.php` | Yes | Yes |
    84→| Doctor approves appointment | `doctor/Appointment.php` | Yes | Yes |
    85→| Doctor marks visited | `doctor/Appointment.php` | Yes | Yes |
    86→| Doctor cancels/rejects | `doctor/Appointment.php` | Yes | Yes |
    87→| Receptionist approves | `receptionist/Appointment.php` | Yes | Yes |
    88→| Receptionist extends | `receptionist/Appointment.php` | Yes | Yes |
    89→| Receptionist marks visited | `receptionist/Appointment.php` | Yes | Yes |
    90→| Receptionist rejects | `receptionist/Appointment.php` | Yes | Yes |
    91→| Hospital creates booking | `hospital/Appoinment.php` | Yes | Yes |
    92→| Hospital approves | `hospital/Appoinment.php` | Yes | Yes (commented out) |
    93→| Assistant approves | `assistant/Appointment.php` | Yes | Yes |
    94→
    95→### 9.3.3 Notification Content Pattern
    96→Every notification contains:
    97→- `title`: Always "Appointment updated"
    98→- `body`: HTML string with clickable link to the appointment detail page (role-specific URL)
    99→- `user_id`: Target user's ID (always a `users.id` reference)
   100→- Notification bodies include `<b>`, `<a href>` tags (stored as HTML, potential XSS)
   101→
   102→### 9.3.4 Notification Views
   103→- **Patient**: `views/front/patient/notifications.php` - Uses Tabler UI, Bootstrap table, `format_date_time()` helper, `UNREAD` highlighted with `table-warning`
   104→- **Doctor**: `views/doctor/notifications.php` - Uses AdminLTE UI, `warning` class for unread, `format_date_time()` helper
   105→- **Receptionist, Assistant, Hospital, Pharmacist**: Each has their own Notifications controller under their respective view directories
   106→
   107→### 9.3.5 Notification Architecture Issues
   108→- No notification channel system (only in-app, no email/push)
   109→- `update()` method updates ALL notifications for a user instead of a single one
   110→- No bulk mark-as-read
   111→- No notification preferences/settings
   112→- Notifications are never deleted, only marked READ/UNREAD

   116→## 9.4 Chat System
   117→
   118→### 9.4.1 Booking_chat_model
   119→- **Table**: `booking_chat`
   120→- **Schema**: id, booking_id, from_id (users.id), to_id (users.id), message (text), status (READ/UNREAD), created_at
   121→- **Methods**:
   122→  - `create($data)` - Creates chat message with auto-timestamp
   123→  - `update($id, $data)` - Updates a chat message
   124→  - `getByAppointment($booking_id)` - Returns all messages for a booking with JOINs to `users` (as `fuser` and `tuser`) for `from_name` and `to_name`
   125→
   126→### 9.4.2 Chat Flow Architecture
   127→```
   128→Patient ----AJAX POST----> appointment/send_chat_msg
   129→                               |
   130→                               v
   131→                    Booking_chat_model->create()
   132→                    (from_id=patient, to_id=receptionist_user_id)
   133→                               |
   134→                               v
   135→                    DB: booking_chat table
   136→                               ^
   137→                               | (5-second polling)
   138→                    get_all_chat_message() <-----AJAX POST---- Patient UI
   139→                    get_all_chat_message() <-----AJAX POST---- Receptionist UI
   140→```
   141→
   142→### 9.4.3 Chat Participants
   143→- **Patient <-> Receptionist**: Chat is enabled between patient and the doctor's assigned receptionist
   144→- Chat is conditionally enabled: only if `$isCheckBoxEnable` is true (i.e., the doctor has a receptionist)
   145→- Chat is disabled when appointment status is `VISITED` or `REJECTED`/`Canceled`
   146→- **Doctor does NOT have chat** - The doctor appointment show view has no chat UI
   147→- **Hospital can also chat** via `hospital/Appoinment` controller
   148→- **Assistant does NOT have chat endpoints** (no `Booking_chat_model` loaded)
   149→
   150→### 9.4.4 Chat UI Implementation
   151→All three chat UIs (patient, receptionist, hospital) are nearly identical:
   152→- jQuery `$.post()` for sending and receiving
   153→- 5-second `setInterval` polling loop
   154→- Renders messages as left/right-aligned bubbles with placeholder avatars from `placehold.it`
   155→- Auto-scrolls to bottom on new messages
   156→- No typing indicator, no read receipts, no file attachments
   157→- No WebSocket/Server-Sent Events (pure polling)
   158→
   159→### 9.4.5 Chat Security Issues
   160→- Messages stored in plain text
   161→- No message length limits
   162→- No spam protection
   163→- Status field exists but is never updated (all messages stay UNREAD)
   164→- Bug in `receptionist/Appointment.php` show view: there's a stray `DGKPM4300J` text on line 229

   169→
   170→### 9.5.1 Doctor_rating_model
   171→- **Table**: `doctor_rating`
   172→- **Schema**: id (bigint), patient_id (int), doctor_id (int), star (int 1-5)

   184→| `Doctors.php` | `doctor_rating` | Display doctor profile with rating |

   186→| `doctor/Dashboard.php` | `doctor_rating` | Show own rating on dashboard |

   188→| `receptionist/Dashboard.php` | `doctor_rating` | Show doctor's rating on receptionist dashboard |
   189→| `hospital/Doctor.php` | `doctor_rating` | Show doctor rating in hospital doctor list |

   193→### 9.5.3 Rating Issues
   194→- `get_average_rating()` uses 5 separate COUNT queries instead of a single GROUP BY
   195→- No decimal precision handling in the star field (no half-star support)
   196→- No review text field, only numeric star rating
   197→- `Api.php` rate_us endpoint: no validation that star value is 1-5
   198→- Rating is per patient-doctor pair (one rating per patient per doctor, updatable)

   216→## 9.7 Prescription System (Shared Across Roles)
   217→
   218→### 9.7.1 Two Prescription Subsystems
   219→
   220→The system has **two separate prescription mechanisms** that coexist:
   221→
   222→#### A. Legacy Prescription (`Prescriptions_model`)
   223→- **Table**: `prescriptions`
   224→- **Schema**: id, booking_id, disease_description (text), medicine_details (JSON text: `[{Name, Description, Tab}]`), remark (text), created_by, user_id (doctor_id)
   225→- **Used by**: `doctor/Appointment` (create_prescription, store_prescription, edit_prescription, update_prescription)
   226→- **Simple structure**: One record per booking with JSON-encoded medicine list
   227→
   228→#### B. Ajax Prescription System (`Ajaxprescription_model` + 6 sub-models)
   229→- **Table**: `prescription` (singular)
   230→- **Schema**: id, doc_id, patient_id, booking_id, next_visit (date), status, created_by, created_at, updated_at
   231→- **Sub-tables** (all linked via `p_id` → `prescription.id`):
   232→  - `p_cos` - Complaints/Observations (category, question, question_code)
   233→  - `p_labels` - Custom labels with values and units
   234→  - `p_medicine` - Individual medicine records (morning, afternoon, evening, tab, doz, description)
   235→  - `p_suggestions` - Suggestions per question
   236→  - `p_digno_table` - Diagnostic table configurations (rows, cols, header/footer labels)
   237→  - `p_other_settings` - Per-doctor prescription print settings (logo, time, header)
   238→
   239→### 9.7.2 Prescription Wizard (6-Step Flow)
   240→
   241→The Ajax Prescription UI is a 6-step wizard:
   242→
   243→```
   244→Step 1: Category Details (CO)     [Stethoscope icon]
   245→  → Select checkboxes from complaints/observations grouped by CO code
   246→  → POST: ajax_insert_co {cos: [[co_code, question, question_code]], pre_id}
   247→
   248→Step 2: Diagnosis Table           [File icon]
   249→  → Table master configuration (dynamic rows/cols)
   250→
   251→Step 3: Medicine Details          [Table icon]
   252→  → Add medicines with autocomplete from doctor_medicine_list
   253→  → Fields: name, doz, morning, afternoon, evening, tab, description
   254→  → POST: ajax_insert_medi_list {lists: [[name,morning,afternoon,evening,tab,doz,desc]], pre_id}
   255→
   256→Step 4: Suggestion Details        [List icon]
   257→  → Checkboxes for predefined suggestions per question
   258→  → Extra text field for custom suggestions
   259→  → Next visit date picker
   260→  → POST: ajax_insert_suggestion {sug: [[question, suggestion]], pre_id, next_date}
   261→
   262→Step 5: Finish                    [Check icon]
   263→  → Success animation
   264→  → "Go Appointment" / "Print Prescription" buttons
   265→```
   266→
   267→### 9.7.3 Prescription Role Access
   268→
   269→| Role | Legacy Prescription | Ajax Prescription | Print |
   270→|------|--------------------|--------------------|-------|
   271→| Doctor | Create/Edit/Store | Full 6-step wizard | Yes |
   272→| Assistant | No | Full 6-step wizard (mirrored) | Yes |
   273→| Patient | View only | View only (print_prescription via Appointment) | Yes |
   274→| Pharmacist | View list | View detail per prescription | No (via controller) |
   275→| Receptionist | No | No | No |
   276→| Hospital | No | No | No |
   277→| Admin | No | No | No |
   278→
   279→### 9.7.4 Prescription Cross-Role Sharing
   280→- The `doctor/AjaxPrescription/print_prescription` view is shared by Patient for printing (patient `Appointment.php` line 146 loads `doctor/AjaxPrescription/print_prescription`)
   281→- Doctor and Assistant have near-identical AjaxPrescription views with only the URL prefix differing (`/doctor/` vs `/assistant/`)
   282→- The AjaxPrescription controllers for doctor and assistant are functionally identical
   283→- Pharmacist accesses via `pharmacist/Pharmacist.php` which loads all P_* models
   284→
   285→### 9.7.5 Prescription Voice Input
   286→- The Ajax Prescription views include **Web Speech API** integration
   287→- Voice recognition activates on focus of medicine name input fields
   288→- Uses `webkitSpeechRecognition` / `SpeechRecognition` API
   289→- Animated GIF indicators (voice_on.gif / voice_off.gif)
   290→- Recognition stops on input blur
   291→- **Browser support**: Chrome only (no fallback)
   292→
   293→### 9.7.6 Prescription Medicine Autocomplete
   294→- Medicine data pre-loaded as PHP JSON into JavaScript (`<?= $list ?>` and `<?= $list_detail ?>`)
   295→- Uses jQuery UI Autocomplete
   296→- On selection, auto-fills: morning, afternoon, evening, tab, doz, description
   297→- Source: `doctor_medicine_list` table (per-doctor medicine master)

   927→## 10.5 State Machines
   928→
   929→### 10.5.1 Booking Status State Machine
   930→
   931→```
   932→                    ┌──────────────────────┐
   933→                    │                      │
   934→         ┌─────────│      PENDING          │
   935→         │         │   (Initial State)     │
   936→         │         │                      │
   937→         │         └──────────┬───────────┘
   938→         │                    │
   939→         │         ┌─────────┼──────────┐
   940→         │         │         │          │
   941→         │         ▼         │          ▼
   942→         │  ┌─────────────┐  │   ┌─────────────┐
   943→         │  │   EXTEND    │  │   │  APPROVE    │
   944→         │  │             │  │   │             │
   945→         │  └──────┬──────┘  │   └──────┬──────┘
   946→         │         │         │          │
   947→         │         │         │   ┌──────┼──────┐
   948→         │         │         │   │      │      │
   949→         │         │         │   ▼      │      ▼
   950→         │         │         │┌────────┐ │ ┌─────────┐
   951→         │         │         ││VISITED │ │ │CANCELED │
   952→         │         │         ││(Final) │ │ │(Final)  │
   953→         │         │         │└────────┘ │ └─────────┘
   954→         │         │         │           │
   955→         │         └─────────┤           │
   956→         │                   │           │
   957→    ┌────┴────┐              │           │
   958→    │ CANCELED │◄─────────────┘           │
   959→    │ (Final)  │◄─────────────────────────┘
   960→    └──────────┘
   961→
   962→TERMINAL STATES: VISITED, CANCELED
   963→
   964→Valid Transitions:
   965→  PENDING  → APPROVE   (by doctor, receptionist, hospital, assistant)
   966→  PENDING  → EXTEND    (by doctor, receptionist)
   967→  PENDING  → CANCELED  (by patient [cancel], doctor [cancel], receptionist [reject])
   968→  EXTEND   → APPROVE   (by doctor, receptionist)
   969→  EXTEND   → CANCELED  (by doctor [cancel], receptionist [reject])
   970→  APPROVE  → VISITED   (by doctor, receptionist)
   971→  APPROVE  → CANCELED  (by doctor [cancel], receptionist [reject])
   972→
   973→Invalid Transitions (blocked in code):
   974→  VISITED → * (any further change blocked)
   975→  CANCELED → * (any further change blocked)
   976→  APPROVE → EXTEND (not allowed)
   977→  APPROVE → PENDING (not allowed)
   978→
   979→Special: Prescription creation sets status to VISITED (via AjaxPrescription controller)
   980→```
   981→

  1003→
  1004→NOTE: Users_model has confusing method names:
  1005→  - update_status_active($id) actually sets status to BLOCK

  1258→=== KEY OBSERVATIONS ===
  1259→
  1260→1. SINGLE TABLE INHERITANCE: The `users` table uses role-based single table inheritance.
  1261→   All 7 roles (admin, hospital, doctor, assistant, receptionist, patient, pharmacist)
  1262→   share one table differentiated by the `role` column.
  1263→
  1264→2. BOOKING IS THE HUB: The `booking` table is the central junction connecting:
  1265→   - Users (doctor_id, user_id/patient)
  1266→   - Chat (booking_chat.booking_id)
  1267→   - Notifications (triggered by booking status changes)
  1268→   - Legacy Prescription (prescriptions.booking_id)
  1269→   - Ajax Prescription (prescription.booking_id)
  1270→
  1271→3. NO DATABASE-LEVEL FK CONSTRAINTS: All relationships are application-enforced only.
  1272→
  1273→4. TWO PARALLEL PRESCRIPTION SYSTEMS: `prescriptions` (legacy, JSON blob) and
  1274→   `prescription` + 6 sub-tables (ajax, normalized) coexist without migration path.
  1275→
  1276→5. MASSIVE CODE DUPLICATION:
  1277→   - doctor/AjaxPrescription/index.php ≈ assistant/AjaxPrescription/index.php (1279 vs 1279 lines)
  1278→   - doctor/AjaxPrescription controller ≈ assistant/AjaxPrescription controller
  1279→   - Chat UI duplicated across patient/receptionist/hospital views
  1280→   - Notification creation pattern duplicated in 4+ Appointment controllers
  1281→
  1282→6. NOTIFICATION BROADCAST: Every booking status change creates 2 notifications
  1283→   (one for patient, one for receptionist if assigned).
