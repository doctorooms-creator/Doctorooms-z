    37→## 1. EXECUTIVE SUMMARY
    38→
    39→### 1.1 The Project
    40→
    41→Doctorooms is a multi-role healthcare appointment management platform being rebuilt from a PHP/CodeIgniter monolith to Next.js 16. It serves 7 user roles: Patient, Doctor, Receptionist, Hospital, Assistant, Pharmacist, and Admin.
    42→
    43→### 1.2 Current State — By The Numbers
    44→
    45→```
    46→Pages:           61 dashboard + 11 public = 72 total
    47→API Routes:      101 files, ~150 endpoints
    48→DB Models:       30 (Prisma)
    49→Dependencies:    47 production, 8 dev
    50→Components:      40+ shadcn/ui + 9 custom
    51→Total LOC:       ~30,000+ (estimated)
    52→```
    53→
    54→### 1.3 Module Completion
    55→
    56→| Module | Pages | APIs | Bugs | Completion | Priority |
    57→|--------|-------|------|------|------------|----------|
    58→| **Patient** | 12 | 30 | 34 | **62%** | 🔴 #1 FIRST |
    59→| **Receptionist** | 14 | 23 | ~12 | **55%** | 🔴 #2 |
    60→| **Doctor** | 13 | 18 | ~15 | **46%** | 🟡 #3 |
    61→| **Hospital** | 3 | 3 | ~5 | **20%** | 🟡 #4 |
    62→| **Assistant** | 3 | 3 | ~3 | **30%** | 🟢 #5 |
    63→| **Pharmacist** | 3 | 3 | ~2 | **25%** | 🟢 #5 |
    64→| **Admin** | 8 | 10 | ~8 | **31%** | 🟢 #6 (LAST) |
    65→
    66→### 1.4 The Core Problem
    67→
    68→> **85% of code is written but only ~45% works end-to-end.**
    69→
    70→The platform suffers from three systemic issues:
    71→
    72→1. **Empty database** — zero seed data, app appears dead to any visitor
    73→2. **5 critical bugs in Patient module** — the money-making flow is broken
    74→3. **No cross-module integration testing** — modules built in isolation, don't connect
    75→
    76→### 1.5 The Architect's Verdict
    77→
    78→```
    79→IF we fix Phase 0 (critical blockers) → Patient module goes from 40% → 80% E2E
    80→IF we complete Phase 1 (patient journey) → Platform has ONE working user flow
    81→IF we complete Phase 2 (workflow)  → Doctor + Reception can process bookings
    82→IF we complete Phase 3 (supporting)  → All roles have functional dashboards
    83→IF we complete Phase 4 (admin)       → Platform is self-service
    84→IF we complete Phase 5 (hardening)  → Production-ready
    85→```
    86→
    87→**Estimated total effort**: 6 development phases × 2-3 sessions each = **12-18 focused sessions**

   171→| Problem | Severity | Impact |
   172→|---------|----------|--------|
   173→| No middleware.ts — all route protection is client-side | HIGH | Pages flash before redirect, no server-side guard |
   174→| 100% client components (zero server components) | MEDIUM | No SSR/SSG benefits, larger JS bundles |
   175→| No Zod validation on API requests | HIGH | Inconsistent validation, security gaps |
   176→| No shared types directory | MEDIUM | Duplicated type definitions, drift risk |

   178→| Session cookie = raw user ID | CRITICAL | Knowing a CUID = full account access |
   179→| Chat WebSocket service exists but unused | MEDIUM | Wasted infrastructure, HTTP polling instead |
   180→| No file upload infrastructure (except avatar) | HIGH | Medical documents upload is fake |
   181→| 3 monolith page files (700-800 lines) | MEDIUM | Hard to maintain, test, reuse |
   182→| No error boundaries | MEDIUM | Uncaught errors crash the UI |
   183→| No NextAuth integration (dead code in auth.ts) | LOW | Confusion, wasted imports |
   184→| No environment variable validation | LOW | Missing NEXTAUTH_SECRET, etc. |

   228→
   229→### 3.2 Architecture Principles
   230→
   231→| # | Principle | Description |
   232→|---|-----------|-------------|
   233→| 1 | **Patient First** | Every decision prioritizes the patient journey. Revenue comes from bookings. |
   234→| 2 | **Validate Everything** | All API inputs validated with Zod. All outputs typed. No exceptions. |
   235→| 3 | **Extract, Don't Duplicate** | Shared logic in `lib/`, `hooks/`, `types/`, `components/`. DRY at all levels. |
   236→| 4 | **Fail Gracefully** | Error boundaries, loading states, empty states, error toasts — always. |
   237→| 5 | **Secure by Default** | httpOnly cookies, ownership checks, input sanitization, no raw IDs in responses. |
   238→| 6 | **Server When Possible** | Use server components for data-heavy pages. Client only for interactivity. |
   239→| 7 | **Batch Over N+1** | Never make N API calls when 1 batch call will do. |
   240→| 8 | **Real-Time Over Polling** | Use WebSocket for chat, notifications, queue positions. |

   244→## 4. ARCHITECTURE DECISION RECORDS (ADRs)
   245→
   246→### ADR-001: Authentication — Custom Cookie (Keep)
   247→
   248→- **Status**: ACCEPTED
   249→- **Context**: System uses custom `doctorooms_session` cookie (raw user ID) instead of NextAuth JWT
   250→- **Decision**: Keep custom cookie auth for API routes. Fix security (add random token, make httpOnly)
   251→- **Rationale**: Works reliably, simple to debug, no NextAuth dependency. NextAuth config exists but is unused dead code.
   252→- **Consequences**: Must add session token rotation and httpOnly flag. Must remove dead `auth.ts` NextAuth config.
   253→
   254→### ADR-002: Validation — Adopt Zod for All APIs
   255→
   256→- **Status**: PROPOSED
   257→- **Context**: Currently all API validation is manual (`if (!body.name) return error`). Inconsistent, missing checks.
   258→- **Decision**: Create Zod schemas for every API request body. Validate at route handler entry point.
   259→- **Rationale**: Zod v4 is already a dependency. Provides type inference, auto-parsing, consistent error messages.
   260→- **Consequences**: ~101 route files need Zod schemas. Schemas go in `src/lib/validations/`.
   261→
   262→### ADR-003: File Upload — Local Disk (Current Phase)
   263→
   264→- **Status**: ACCEPTED
   265→- **Context**: Medical document upload is fake (metadata only). Avatar upload works but writes to `public/`.
   266→- **Decision**: Phase 1-3: Local disk (`uploads/` with Bun file API). Phase 4+: Abstract to storage interface for S3/GCS.
   267→- **Rationale**: SQLite + local disk is sufficient for dev/MVP. Production needs cloud storage.
   268→- **Consequences**: Need `src/lib/storage.ts` abstraction layer. File serving via Next.js API route (not public/).
   269→
   270→### ADR-004: Real-Time — Socket.io (Existing Service)
   271→
   272→- **Status**: PROPOSED
   273→- **Context**: Chat service exists at `mini-services/chat-service/` (port 3003) but is unused. All real-time is HTTP polling (10s).
   274→- **Decision**: Activate Socket.io for: (1) Chat messages, (2) Notification push, (3) Queue position updates, (4) Booking status changes.
   275→- **Rationale**: Service exists, just needs wiring. Eliminates 10s polling. Better UX for chat.
   276→- **Consequences**: Frontend needs Socket.io client. Auth needs to pass through gateway.
   277→
   278→### ADR-005: Component Architecture — Extract From Monoliths
   279→
   280→- **Status**: PROPOSED
   281→- **Context**: 3 page files are 700-800 lines. `StarRating` duplicated. `statusColors` in 4+ files.
   282→- **Decision**: Decompose monolith pages into focused components. Extract shared pieces to `src/components/` and `src/hooks/`.
   283→- **Rationale**: Maintainability, testability, reusability. Pages should be orchestrators, not implementations.
   284→- **Consequences**: Each 800-line file becomes 1 page (200 lines) + 4-5 components (100-150 lines each).
   285→
   286→### ADR-006: Types — Centralize in `src/types/`
   287→
   288→- **Status**: PROPOSED
   289→- **Context**: All types are inline in page files. `AuthUser` duplicated. `statusColors` in 4 files.
   290→- **Decision**: Create `src/types/` with domain-specific type files. Import from there.
   291→- **Rationale**: Single source of truth. Auto-completion. Prevents drift.
   292→- **Consequences**: Need to create type files, then update all imports across 61+ pages.
   293→
   294→### ADR-007: Database — Stay SQLite for Dev, Prepare PostgreSQL Migration
   295→
   296→- **Status**: ACCEPTED
   297→- **Context**: Current DB is SQLite. `.env.example` shows Supabase PostgreSQL config (commented out).
   298→- **Decision**: Keep SQLite for all development. Schema must be PostgreSQL-compatible (no SQLite-specific features). Migration script exists at `scripts/switch-to-supabase.sh`.
   299→- **Rationale**: SQLite is zero-config for dev. Prisma abstracts the DB layer. Switch is one config change.
   300→- **Consequences**: No raw SQL queries. No SQLite-specific functions. Test migration before production.
   301→
   302→### ADR-008: Middleware — Add `middleware.ts` for Route Protection
   303→
   304→- **Status**: PROPOSED
   305→- **Context**: Currently all dashboard route protection is client-side (useEffect in layout). Pages flash before redirect.
   306→- **Decision**: Add Next.js `middleware.ts` that checks `doctorooms_session` cookie and redirects unauthenticated users to `/login`.
   307→- **Rationale**: Server-side protection prevents flash. Faster redirect (no JS execution needed). More secure.
   308→- **Consequences**: Middleware can't do DB lookups (edge runtime). Cookie-only check is sufficient for redirect — API routes still do full auth.

   875→## 14. API ARCHITECTURE STANDARDS
   876→
   877→### 14.1 Route Handler Template
   878→
   879→Every API route MUST follow this pattern:
   880→
   881→```typescript
   882→// src/app/api/example/route.ts
   883→import { NextRequest, NextResponse } from 'next/server';
   884→import { requireRole } from '@/lib/api-auth';
   885→import { db } from '@/lib/db';
   886→import { z } from 'zod';
   887→
   888→// 1. Validation schemas (at top of file)
   889→const CreateBodySchema = z.object({
   890→  name: z.string().min(1, 'Name is required').max(100),
   891→  email: z.string().email('Invalid email'),
   892→  status: z.enum(['Active', 'Inactive']).optional(),
   893→});
   894→
   895→// 2. Type inference from schema
   896→type CreateBody = z.infer<typeof CreateBodySchema>;
   897→
   898→// 3. Route handler
   899→export async function POST(req: NextRequest) {
   900→  // 3a. Auth check
   901→  const user = await requireRole(req, 'patient');
   902→  if (!user) {
   903→    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   904→  }
   905→
   906→  // 3b. Parse + validate body
   907→  let body: CreateBody;
   908→  try {
   909→    const raw = await req.json();
   910→    body = CreateBodySchema.parse(raw);
   911→  } catch (err) {
   912→    if (err instanceof z.ZodError) {
   913→      return NextResponse.json(
   914→        { error: 'Validation failed', details: err.errors },
   915→        { status: 400 }
   916→      );
   917→    }
   918→    return NextResponse.json({ error: 'Invalid request body' }, { status: 400 });
   919→  }
   920→
   921→  // 3c. Business logic
   922→  try {
   923→    const record = await db.example.create({
   924→      data: { ...body, userId: user.id },
   925→    });
   926→    return NextResponse.json({ record }, { status: 201 });
   927→  } catch (error) {
   928→    console.error('POST /api/example:', error);
   929→    return NextResponse.json(
   930→      { error: 'Internal server error' },
   931→      { status: 500 }
   932→    );
   933→  }

   950→### 14.3 Auth Patterns
   951→
   952→```typescript
   953→// Role-required (most common)
   954→const user = await requireRole(req, 'patient');
   955→if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   956→
   957→// Any authenticated user
   958→const user = await requireAuth(req);
   959→if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   960→
   961→// Ownership check (after auth)
   962→if (record.userId !== user.id) {
   963→  return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
   964→}

  1043→### 16.3 Schema Design Principles
  1044→
  1045→1. **No SQLite-specific features** — use only Prisma-compatible types
  1046→2. **All strings have `@default('')`** — never null strings
  1047→3. **All numbers have `@default(0)`** — never null numbers
  1048→4. **Optional fields use `?` type** — explicit nullability
  1049→5. **JSON fields use `String` type** — Prisma SQLite doesn't support Json type natively
  1050→6. **Cascade deletes** — use `onDelete: Cascade` for owned relationships

  1207→## 20. RISK REGISTER & MITIGATION
  1208→
  1209→| # | Risk | Probability | Impact | Mitigation |
  1210→|---|------|-------------|--------|------------|
  1211→| R-1 | **Seed data becomes stale** | Medium | Medium | Create idempotent seed script that can be re-run. Add `--force` flag to reset. |
  1212→| R-2 | **SQLite limits hit in production** | Low | High | Keep schema PostgreSQL-compatible. Test migration before production. |
  1213→| R-3 | **Session security breach** | Medium | Critical | Phase 0: httpOnly. Phase 5: Random tokens. Phase 5+: Refresh rotation. |
  1214→| R-4 | **Monolith pages become unmaintainable** | High | Medium | Phase 5 decomposition. Keep new pages under 400 lines. |
  1215→| R-5 | **N+1 queries cause performance issues** | High | Medium | Phase 2: Batch APIs. Phase 5: DataLoader pattern if needed. |
  1216→| R-6 | **Module integration breaks existing flows** | Medium | High | Phase 2: End-to-end integration test. Browser verification after each phase. |
  1217→| R-7 | **Scope creep in Phase 3-4** | High | Medium | Strict phase boundaries. No new features in hardening phase. |
  1218→| R-8 | **File uploads fill disk** | Low | Medium | Add file size limits. Phase 5: Add storage quotas per user. |
  1219→| R-9 | **Chat service crashes** | Low | Medium | Graceful fallback to HTTP polling if WebSocket fails. |
  1220→| R-10 | **Doctor schedule conflicts** | Medium | Medium | Already handled by check-slot API. Add database-level unique constraint for same doctor/date/slot. |
